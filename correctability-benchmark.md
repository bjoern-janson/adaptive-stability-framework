# THE CORRECTABILITY BENCHMARK

**Spec v0.1 — measuring whether a memory system stops trusting what misled it.**

**Westfield Innovations · for implementation**

---

## Why this benchmark and not the RAG one

Retrieval accuracy against a vector database measures how well we find text that matches a query. Every memory product on the market competes there, and it is not what PDM is built to do differently.

PDM's distinctive claim is that memories which mislead **LOSE authority** and memories which prove out **GAIN it** — the Validation Coefficient.

That is a claim about behavior over time, and no static-text memory system can even be tested for it, because a stored chunk has no authority to lose.

So this benchmark measures the one thing only we can win:

> Does the system get less wrong the longer it runs.

That produces the number an enterprise evaluator actually cares about, and it is a number our competitors cannot report.

---

# The core question

A high-authority memory makes a wrong prediction.

A lower-authority memory made the right one.

Reality returns the verdict.

Does the wrong memory's authority fall — or does it stay dominant and keep being wrong?

We call the failure mode **MEMORY GRAVITY**:

> an established signature that outranks a correct one purely because it got there first.

---

# Setup

- **Scenario:** a question with a single verifiable ground-truth answer, known to the harness and not to the system.

- **Competing pair:** for each scenario, seed two memories.

  - Signature A: the **WRONG** answer, seeded at high p_magnitude (say 85).
  - Signature B: the **CORRECT** answer, seeded low (say 40).

  Both tagged so both surface as candidates for the same query.

- **Scale:** minimum 100 scenarios across at least 4 domains, so the result is not an artifact of one topic.

  5 random seeds, report mean and variance.

- **Round:** one full cycle:

query
→
retrieve
→
the top hit is used as the answer
→
harness compares to ground truth
→
consequence signal fed back through the normal API

(reinforce on hit, the system's own penalty path on miss)

No special-case code: the benchmark must exercise the shipping path, not a test path.

- **Run length:** 20 rounds per scenario, or until crossover, whichever comes first.

---

# The five numbers

## 1. Crossover round (headline number)

The round at which:

P_B first exceeds P_A

Lower is better.

Report the median and the distribution, not just the mean — the tail is where memory gravity hides.

---

## 2. Memory gravity index

The percentage of scenarios where the **WRONG** signature is still dominant at round 20.

Target is zero.

This is the number that kills us if it's high, and the number that sells us if it's low.

---

## 3. Error curve

Accuracy per round, averaged across scenarios.

The claim is that this curve rises.

Plot it — the picture is the marketing asset.

---

## 4. Authority decay slope

dP/dt

of signature A after its first failure.

Measures how decisively the system demotes a proven-wrong memory.

---

## 5. False demotion rate

Percentage of **CORRECT** signatures that lose dominance due to noise or an unlucky round.

Guards the opposite failure:

A system so twitchy it forgets things that were right.

A good result needs:

#2 low AND #5 low

# Baselines to run alongside

*(this is what makes it publishable)*

## Ablation — PDM with the Validation Coefficient disabled

The most important comparison in the whole benchmark.

Same system, mechanism off.

If V is doing the work, this run should show:

- high memory gravity
- a flat error curve

This isolates **OUR mechanism** and proves the result is not an accident of retrieval.

---

## Vector-DB RAG

Standard embedding retrieval, no authority update.

Expected:

- memory gravity near 100%
- error curve flat

It cannot correct because there is nothing in it that can be demoted.

---

## Keyword + recency

The naive baseline, for completeness.

# Implementation notes

Run through the public SDK surface only:

Memory.save
Memory.recall
Memory.reinforce

and whatever the shipping penalty path is.

If the benchmark needs an internal hook that a customer doesn't have, that hook belongs in the API or the result isn't real.

```bash
python -m pdm_memory.bench --suite correctability --rounds 20 --seeds 5
````
Emit JSON with per-round, per-scenario records so the plots can be regenerated by anyone.

Ship the scenario set in the repo so an outside developer can run it and get our number.

> A benchmark nobody can reproduce is marketing; a benchmark anyone can run is a receipt.

---

# What counts as a good result

A successful result means:

- Median crossover inside a handful of rounds
- Memory gravity index near zero
- A visibly rising error curve
- False demotion rate low
- V-disabled ablation clearly worse than V-enabled

If we get that, it is:

- A blog post
- A README section
- A line in any licensing conversation

And if we **DON'T** get it — if PDM shows memory gravity too — that is a bug in the mechanism we most need working, found by us instead of by a customer.

Either outcome is worth the day it takes to build.
